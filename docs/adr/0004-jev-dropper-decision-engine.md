# Jev as the dropper decision engine with LLM fallback

When `dropper.mode` is `"jev"`, the dropper stage asks TypeSafe System One (Jev) one noul question per active observation instead of running the LLM agent loop. A noul at or above 0.8 proposes the observation for dropping; proposals feed the existing deterministic ranking (`selectDropCandidates`), so reflection coverage, relevance, age ordering, and the per-run drop cap behave identically to the LLM path. The threshold is a code constant (`JEV_DROP_NOUL_THRESHOLD`), tuned against the pinned `jev-1.13.0`, not a config knob: a user-set threshold near 1 would be silently masked by config validation, and the phase 0 calibration does not transfer across model ids.

The state sent to Jev contains the pool briefing, reflection summary lines, and one fact per active observation: id, content, relevance, coverage tier, and age in whole minutes. Age is computed in code because Jev does no date arithmetic, and observations are ordered oldest-first so position carries age order. Requests are chunked with a conservative character-class token estimator against the serialized state-plus-questions body (the same basis the API bills); a chunk that cannot fit even one observation fails the whole run (`state_too_large`) rather than sending a request that risks the API's 32k state ceiling.

Failure is all-or-nothing per run. Transport errors (bad key, invalid request, payload too large, rate limit, overload, network, timeout, malformed response) and oversized states drop nothing from Jev and hand the same run to the LLM dropper; a zero-drop success is a normal outcome, not a fallback. The fallback is lazy: the LLM model resolves only after Jev fails, so a healthy Jev mode never pays for model resolution. The first fallback per session notifies once — `dropper using LLM fallback — Jev unavailable (<reason>)` — so a missing key or misconfigured mode is never silent; later fallbacks only log `dropper.jev_fallback`. The API key comes from an environment variable (`TYPESAFE_API_KEY` by default, overridable via `dropper.jev.apiKeyEnv`) and is never written to settings or logs.

## Considered options

Making the threshold and chunk budget configurable was rejected: both are tuned against the pinned model, the threshold interacts with config validation (a value outside (0,1) would be silently dropped), and no eval yet demands tuning. Mixing verdicts from both engines in one run was rejected: appending Jev-proposed and LLM-proposed drops together makes outcomes non-reproducible and doubles the decision surface per run. Sharing the Jev transport seam beyond the dropper is deferred to the planned context lens; the client and estimator are reusable but only the dropper consumer ships now. Fanning chunk requests out concurrently was rejected: sequential chunks stay within the documented rate limits and keep failure attribution simple.

## Consequences

Dropper decisions in `"jev"` mode are input-only and cheap (about $0.042 per million input tokens), and each observation is an independent judgment, so a pool that outgrows the LLM context still gets decided. The all-or-nothing fallback bounds the blast radius of transport changes: a bad response never drops anything. The LLM dropper remains the default and its behavior is unchanged. New debug events (`dropper.jev_start`, `dropper.jev_chunk`, `dropper.jev_result`, `dropper.jev_fallback`) make fallback reasons auditable. The `JevClient` seam and the token estimator are the reusable Phase 2 surface; nothing in them is dropper-specific except the drop questions and state shape, which live in the dropper module.
